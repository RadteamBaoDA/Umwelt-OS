## Delivered in R03-core

- Added a connector catalog with truthful provider, authentication, scope, collection-mode, capability, and availability metadata. OAuth-dependent capabilities remain unavailable until the authorized provider consumer is implemented.
- Added durable provisioning state and managed-credential references, optimistic desired revisions, secret replacement/removal flows, protected n8n credential API operations, and ARQ reconciliation for stale activation intents, pending deactivation, and provider credential deletion.

- Generated workflows bind the source ID, source generation, desired revision, and real n8n credential references. Removed the global `SOURCE_ID` setting.
- Added connector deactivation and provider-credential removal, with collector-token revocation inside the caller transaction. The generic owner source PATCH pause path now also revokes existing collector tokens under the source row lock, preventing a later resume from re-enabling an old token.
- Added the provisioning migration and indexes for reconciliation queries; updated connector setup copy and operator guidance. The richer in-app connector editor remains R04 scope.

  6. **Ambiguous credential PATCH:** credential timeout/transport/5xx keeps the exact dispatched envelope and fences newer operations (`modules/connectors/credentials.py`, `modules/connectors/provisioning.py:fail_credential_operation`).
  7. **Revoked collector credential on resume:** activation compares the stored collector binding to current source generation and prepares a persisted token rotation when it differs (`modules/connectors/provisioning_routes.py:_ensure_collector_credential`, `modules/connectors/worker.py:_resume_activation`).

  9. **Credential deletion race/ack:** delete intent is created under owner locks for an exact target ID and operation; acknowledgement checks operation, target, and dispatched state before clearing (`modules/connectors/provisioning.py:create_delete_intent`, `acknowledge_credential_delete`, `modules/connectors/worker.py:_delete_credential`).
  10. **Workflow operation serialization/stale cleanup:** persisted prepared/dispatched steps gate each effect; acknowledgements recheck current generation/revision and queue exact-ID deactivation for stale results. Unknown dispatched operations remain fenced (`modules/connectors/provisioning.py:claim_workflow_step`, `acknowledge_workflow_step`, `fail_workflow_step`, `drive_workflow_operation`).
  11. **Credential binding reuse:** protected immutable input and resolved binding are persisted; ready IDs are reused only when the current header/source binding matches, otherwise explicit replacement or reconciliation is required (`modules/connectors/provisioning.py:create_credential_intent`, `complete_credential_operation`, `modules/connectors/provisioning_routes.py:_ensure_managed_credential`).
  12. **Lock order:** credential claim, completion, failure, delete, workflow, and source-fence transitions share source → provisioning → credential order through `lock_connector` (`modules/connectors/provisioning.py`).
  13. **Deterministic activation rejection:** missing/mismatched prerequisites are rejected before workflow dispatch; known 422 setup failures are guardedly returned to saved-not-active while unknown operations stay fenced (`modules/connectors/provisioning_routes.py:activate_source`, `modules/connectors/provisioning.py:reject_activation`).
