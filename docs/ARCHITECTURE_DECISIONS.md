## 2026-10-06: Per-owner Documents cleanup stages and Source coverage gate

Documents cleanup runs as per-owner stages (Memory, Agents, Notifications/Automations, saved briefs), each with its own isolated cursor, plus an all-stages aggregate that must settle before a child is complete. Whole-Source purge success is gated on Source historical Documents receipts and Source-local Memory coverage (`p12_source_coverage`), so previously `succeeded` operations are reopened to `running` until coverage re-settles. Legacy brief coverage is bounded by the Document's earliest version timestamp. Build/review evidence only; runtime and physical-erasure acceptance remain pending.

## Whole-Source document cleanup

Whole-Source deletion records its canonical capture/deletion stage on `SourcePurgeOperation` and creates one Documents-owned `DocumentCleanupOperation` receipt per document before the document cascade. The indexed nullable `source_purge_operation_id` linkage and unique partial `(source_purge_operation_id, document_id)` index keep child aggregation owner-local; immutable version/chunk IDs are copied into detached Documents evidence references with `INSERT … SELECT`. Source callers receive only a bounded Documents progress DTO with counts and pending owner codes.

The existing atomic ceiling remains 10,000 Documents. Documents locks document rows in UUID order, then locks exact distinct raw URI identities in lexical order inside PostgreSQL before creating publication fences. It emits bounded operation-only child cleanup events in the same transaction as the evidence capture and canonical cascade. The Source worker never snapshots a URI array or unlinks files; each Documents consumer takes URI-before-receipt locks, rechecks terminal stage state and surviving document references, contains the path, and performs idempotent unlink before commit. `retained_shared` is terminal and the receipt continues to fence later publication.

The Source operation reaches `succeeded` only after successful Documents capture/deletion and every required child stage is complete; an empty source is complete only with the recorded successful capture/deletion receipt. Nonempty sources remain visibly `running` while required copied owners are missing; pending owner codes are still reported and Chat/raw success is not promoted to full erasure. Source success now also requires historical Documents receipts and Source-local Memory coverage (`p12_source_coverage`); all runtime, physical-erasure, restore, capacity, provider and test acceptance remains PENDING. Documents commits deterministic, operation-only `source.purge.progressed` events with actual terminal child-stage changes; distinct UUIDs per bounded stage token prevent a delayed older aggregate observer from consuming a newer wakeup. Future owner integrations must use that Documents seam with stable owner/status progress tokens, preserve the child-receipt lock order, and arrange bounded startup reconciliation for old pending children.

The existing authenticated `/api/v1/system/operations/{id}` source-progress poll uses a Sources-owned, explicit `OperationRead` allowlist. It returns 404 for unknown or non-Source operation IDs and never exposes internal outbox payloads or legacy raw URI arrays.

The migration marks legacy `running`, `succeeded`, and uncertain `failed` Source operations `unavailable`: earlier workers may already have cascaded rows without preserving immutable identities, and `raw_uris` cannot prove copied evidence cleanup. Old `queued` operations remain captureable because the prior worker committed its queued-to-running state in the same transaction as the cascade; a failed `source_generation_changed` receipt remains a truthful failure. New operations leave legacy `raw_uris` empty. No compatibility worker blindly unlinks that JSON; legacy raw repair and all future copied-owner cleanup remain incomplete, and full behavioral/capacity acceptance is deferred.

## 2026-10-09: Optional connector services

Browser and n8n are optional overlays. `docker-compose.connectors.yml` keeps n8n and `include`s `docker-compose.browser.yml` (Compose >= 2.20) so the legacy command still gets both; api/worker network attachments and `BROWSER_SHARED_TOKEN` moved to the browser overlay, and n8n variables reach api/worker via `env_file: .env`. Health lists `n8n` and `browser` as `optional` and excludes them from `overall`. `CatalogEntry.requires_service` records which sidecar a provider needs.

## 2026-10-13: Backend concurrency and data-lifecycle decisions

Implemented on `feature/fix-ui` (uncommitted); verified by offline unit tests only, not under load or on a live database.

**Model gateway circuit breaker in Redis, per upstream.** Context: every worker retried a dead provider independently, holding leases and slots. Decision: a Redis breaker keyed by `gateway_identity` (5 counted failures in 60 s opens it for 30 s; provider `Retry-After` honored up to 300 s), `ModelGatewayUnavailable(retry_after)` while open, jittered retries, probe/discovery bypass as the reset path, fail open on Redis errors. Connectors, n8n, Langfuse and Graphiti keep their own backoff. Consequence: Chat and extraction fail fast during an outage; the breaker is advisory and invisible except in logs.

**No database lock across external I/O.** Context: timeline/entity extraction held Workspace, Source and Document row locks through the model call, so unrelated writers and chat sends waited on a remote provider. Decision: extraction runs in three phases (lock and validate, roll back, infer, re-lock and compare, publish; a mismatch is a retryable error); chat retrieval commits before rerank and web search; SSE paths drain the write buffer before taking the publication or realtime lock. Consequence: extra re-validation work and a retry on concurrent change. Open: temporal `_fresh_fact_action` still violates the rule (needs durable intent plus reconciliation); the global privacy and replay locks stay by design for a single owner.

**Backup activity journal keeps only in-flight rows.** Context: `p12_backup_activity` grew by roughly 170k rows per day because finished activities were kept. Decision: `finish_activity` deletes the row (only `active`/`uncertain` remain, which is all the quiescence check reads). Consequence: no history of finished activities in this table; a Redis journal was rejected because admission needs atomicity with the advisory lock and epoch.

**Independent reconcilers stay independent (tried and rejected 2026-10-13).** Context: the eight 5-second reconcilers each wrote a backup-activity row per run, so merging them into one sequential `reconcile_tick` cron looked like a cheap way to cut activity writes and worker slots. Decision: not merged. In the disposable Compose stack `test_chat_attachment_lifecycle` took about 60 s on the committed code and 673-714 s (failing on the 600 s CSRF cookie lifetime) with the merge, and passed again in 61 s after reverting it. Cause: a tick cannot overlap itself, so one slow or blocked reconciler delays every other reconciler and stretches the whole group's cadence, while separate arq jobs isolate each reconciler's latency and failures. Consequence: the reconcilers remain separate crons; row growth in `p12_backup_activity` is handled by deleting rows on finish. The slowest reconciler of the merged run was not identified.

**Retention instead of unbounded append tables.** Context: observations, stream deltas, receipts, outbox events and automation runs had no purge. Decision: dedupe at intake where the document layer already dedupes, and bounded scheduled deletes with fixed windows (inventory in operations.md). Consequence: raw delta and old receipt history is not recoverable; windows are defaults that the owner has not tuned.

**Keep the asyncio loop; no extra thread or process pools.** Context: uvloop was considered. Decision: stay on `--loop asyncio` because the MCP stdio adapter uses `loop.subprocess_exec` and private transport attributes; offload only specific blocking calls (`to_thread_joined`, parsing) and bound latency of DNS with `wait_for`. Consequence: no loop speedup; `wait_for` does not stop an already running resolver thread.

**Vector search as one query using the existing partial HNSW index.** Context: `ORDER BY dist, chunk_id` and a parameterized generation prevented index use. Decision: keep a single filtered JOIN, order only by the distance expression inside, tie-break outside, inline the generation literal, set `hnsw.iterative_scan=relaxed_order` and `ef_search=100`. A two-stage inner `LIMIT` was rejected because tight filters would drop results. Consequence: recall and latency are unmeasured on real data; compare against exact scan during the capacity test.
