# Umwelt-OS architecture decisions

Design revision: 2026-09-30. The 2026-09-25 approved architecture, including OmniRoute, is retained and extended by canonical spec sections 165–166 following the owner's consolidation request. Phase 0 implementation and acceptance checks are complete; validation on the target mini PC and later-phase integrations remain open. These design decisions do not establish implementation completion. The full delivery index is [the master plan](superpowers/plans/2026-09-25-umwelt-os-master-plan.md); task progress is recorded in [the execution ledger](superpowers/plans/EXECUTION.md). Plans require reconciliation with the latest spec before implementation resumes.

| Decision | Reason | Alternatives | Consequences |
| --- | --- | --- | --- |
| Keep Python/FastAPI, ARQ, and LangGraph; no Go backend initially | Reuse existing queue and agent frameworks to accelerate delivery | Go core plus Python AI worker; custom Go harness | One backend ecosystem; application-specific permissions, idempotency, and recovery integration remain necessary |
| Replace LiteLLM with OmniRoute | Owner already intends to use OmniRoute for multiple AI sources | LiteLLM; direct provider SDKs | Validate actual model capabilities; keep logical aliases and enforce privacy across fallback |
| Use n8n for external collection schedules and packaged workflows | Reuse connectors rather than write every provider integration | Native connectors for all sources | n8n required for these sources; source-available licensing must be represented accurately; mapping/cursor integration still required |
| Crawlee first, browser-use only when needed | Minimize browser/AI work on a small host | Crawl4AI; Browserless; all-browser crawling | One bounded browser task; browser isolation and source provenance remain mandatory |
| Retain Graphiti; choose backend after validation | Preserve temporal knowledge scope without making unsupported compatibility or RAM claims | PostgreSQL-only graph; remote graph backend | Backend selection is a pre-implementation gate for graph work, not permission to omit the feature |
| Target 2 cores and 8 GB with remote inference | Match the owner's hardware | Larger host; remote graph/browser services | Bound jobs, prebuild images, measure the complete enabled stack; no unmeasured capacity guarantee |
| Use an on-demand large shadcn Sheet drawer and a full Chat page sharing one conversation | Owner selected the minimal drawer in section 165 | Permanent chat column; separate-only chat | Drawer contains New chat, messages, composer/send-stop and close; history/context/advanced controls belong to full Chat; closing does not cancel generation; port relevant AnythingLLM source into Umwelt-OS |
| Save brief revisions; show current records for a selected historical day | Owner selected saved brief plus updated lists | Full dashboard state snapshot per day | Date/timezone remain visible; current task state is not represented as historical truth; chat context is bound to the selected day's conversation |
| Save all Phase 1–12 plans and continue ready tasks in native execution | Owner requested local checklists and continuous progression through approved scope | Repeated per-phase planning/approval | Maintain task evidence and next task in EXECUTION.md; external gates remain explicit; no automatic commits or deployments |
| Use Next.js 16.3.6 in Phase 0 | The initially selected Next.js 15 dependency tree resolved a vulnerable PostCSS version; the pinned Next 16 release supports the installed Node 24 runtime and `npm audit` reports no vulnerabilities | Override nested dependencies; defer framework setup | Revisit with scheduled dependency updates and rerun security/build checks |
| Keep all normal connector administration inside Umwelt-OS | Owner does not want to open another administration app | Configure credentials/workflows in n8n UI | Server adapters reconcile packaged workflows and credential references through supported APIs; provider OAuth consent and deployment-time app registration remain necessary |
| Use SSE for dashboard events and run-scoped chat streams; REST for commands | Server-to-browser updates and chat streaming are the current need | WebSocket baseline | Authenticated streams, bounded replay, heartbeat/backpressure and snapshot recovery are required; source polling remains distinct from browser delivery |
| Support MCP client connections and scoped Umwelt-OS MCP server tools | Integrate external tools/data and expose authorized knowledge | Provider APIs only | Configure external MCP under Data sources; prefer Streamable HTTP; stdio is administrator-managed; collection needs its own adapter semantics and actions enforce approval |
| Add Google OAuth/OIDC sign-in to the existing single-owner auth | Owner requested login through Gmail/Google | Password-only auth; independent auth stack | Secure owner linking, state/nonce/PKCE and identity validation; login scopes do not grant Gmail collection; Google-only versus password fallback remains unresolved, so do not remove password login |
| Use PostgreSQL/pgvector and protected files as baseline storage | Preserve current architecture and reduce host overhead | Separate time-series/vector stores | Store time-series observations in PostgreSQL initially; Graphiti backend remains a compatibility/resource gate |

The canonical updated design is `specs/personal-intelligence-os-spec-v2.md`, especially sections 156–166. Sections 165–166 override conflicting earlier UI and connector examples. The proposed PostgreSQL-only queue, custom Go agent runtime, and PostgreSQL replacement for Graphiti were not selected. No Airbyte service or WebSocket baseline is selected. Main navigation remains Dashboard / Chat / Settings, with three Settings groups and account/appearance/language in the user menu.
