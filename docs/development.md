# Development

Install Python 3.12, uv, Node.js 24/npm, and Docker Compose v2.24 or newer. Run `./scripts/dev.ps1 setup` in Windows PowerShell or `make setup` on macOS/Linux. Setup creates `.env` only when missing, then installs locked Python and npm dependencies.

Run the hot-reload stack with `./scripts/dev.ps1 dev` or `make dev`. The frontend is at `http://localhost:3000`. Only its loopback port is published; API, PostgreSQL, and Redis stay on the Compose network. To stop services without deleting data, use the matching `stop` command. Full guideline (modes, LAN access, native run, troubleshooting): `docs/local-development.md`.

For fictional Phase 1, 8, 10 and 12 data, run `./scripts/dev.ps1 seed` or `make seed` after setup. Seeding is explicit and never runs at startup. Stable per-phase owner receipts preserve edits/deletions and ensure the existing `bbd-os.demo.phase-1` source sentinel cannot suppress newer P12 fixtures. P12 adds a project entity, linked person, relationship, manual timeline event, normalized fictional article, and an example conversation only when the owner's durable-history setting permits it. Tasks/goals/topics and disabled automation examples reuse their existing owner seed helpers. A receipt prevents deleted fixtures from being recreated by later seed runs.

To run an isolated local stack, use a unique project such as `bbd-os-ws-a1b2c3d4e5f6`: `./scripts/dev.ps1 dev -Workspace bbd-os-ws-a1b2c3d4e5f6` or `make workspace-up WORKSPACE=bbd-os-ws-a1b2c3d4e5f6`. Each workspace uses project-prefixed named volumes, a project network, and a separately selected loopback web port. Workspace commands force API, worker, and migration database/Redis URLs to those project-local services, regardless of application URLs inherited from `.env`. First registration refuses pre-existing project containers, volumes, or networks and records the Docker daemon ID. Seed it with `./scripts/dev.ps1 seed -Workspace <name>` or `make workspace-seed WORKSPACE=<name>`. Before clearing it, run `./scripts/dev.ps1 reset-preview -Workspace <name>` or `make reset-preview WORKSPACE=<name>`, inspect the name and fingerprint, then pass the exact fingerprint to `./scripts/dev.ps1 reset -Workspace <name> -ConfirmFingerprint <fingerprint>` or `make reset WORKSPACE=<name> CONFIRM_FINGERPRINT=<fingerprint>`. Reset refuses the default project, unregistered workspaces, a changed Compose fingerprint, unexpected volumes/networks, and containers whose Compose project/checkout labels do not match. It deletes only the named local development workspace's Compose resources; owner datasets in shared/external databases are not a supported reset target.

The first-run form requires `SETUP_TOKEN` from the local `.env` file and a password of 12–128 characters. The setup token is separate from the owner password. The application stores only password/session hashes. Do not paste secrets into issues, screenshots, or shared logs.

During production implementation, CI runs dependency installation and the production build only. After all original and reconciliation production tasks are complete, manually dispatch the CI workflow with **Run deferred validation** enabled to run lint, typecheck, and tests. Locally, `test` creates an isolated Compose project and cleans only its uniquely named test volumes on exit. To run only the backend unit tests during the deferred validation stage, use `uv run pytest -q`; frontend lint/typecheck commands are `npm run lint` and `npm run typecheck`.

To run only the browser (Playwright) specs without the slow integration pytest, use `make e2e` (optionally `E2E_TARGET=tests/e2e/<spec>.spec.ts`) or `./scripts/dev.ps1 test -E2eOnly` (optionally `-E2eTarget <spec>`). It builds a uniquely named disposable Compose project, applies `scripts/sql/e2e-reset.sql`, bootstraps the owner login itself (`E2E_SETUP_TOKEN` is set to the disposable token and `auth.spec.ts` saves the session to `playwright/.auth/owner.json`; no manual password entry), runs a single Playwright process (`workers: 1`, `fullyParallel: false`) against the stack, and always runs `down --volumes` on exit.

Optional real-model chat e2e: copy `.env.e2e-real.example` to `.env.e2e-real` (gitignored), fill `E2E_REAL_BASE_URL` (https, OpenAI-compatible, with `/v1`), `E2E_REAL_API_KEY`, `E2E_REAL_MODEL`, and set `E2E_REAL_EXPECT_REASONING` / `E2E_REAL_EXPECT_TOOLS` to `true` if the model supports them. With a non-empty key the harness sets `E2E_ALLOW_PUBLIC_PROVIDERS=true` so the disposable stack (`AI_ALLOW_PUBLIC_PROVIDERS`) may reach public https hosts; otherwise egress stays pinned to the fake model. Run `./scripts/dev.ps1 test -E2eOnly -E2eTarget "auth|chat-real-model"` (or `E2E_ONLY_RUN=1 E2E_TARGET="auth|chat-real-model" ./scripts/test.sh`). The spec is skipped when the key is empty, disables Playwright traces, removes the provider afterwards and asserts the key is never rendered. Revoke the key when done.

Migrations are managed through Alembic. Run `migrate` for an existing local stack; startup also runs the one-shot migration service and waits for success. Do not manually edit a live database schema. The former migration chain is squashed into the baseline `0001_init` (no upgrade path from older databases: recreate the database); later revisions apply on top of it. `0002_observations_provider_ids` widens the `observations.provider` CHECK to every measurement provider id in `MEASUREMENT_PROVIDER_IDS`; without it, measurement-provider sources other than Alpha Vantage and Open-Meteo fail normalization with `retry_exhausted`. Its downgrade refuses to run while such rows exist. Row ids are application-generated UUIDv7 (`core.ids.uuid7`; the web client uses `apps/web/src/core/uuid7.ts`); `uuid_generate_v7()` exists only for set-based `INSERT ... SELECT` paths.

Account deletion recovery runs in the general worker at startup and every 30 seconds. If the browser receipt is lost, the host can inspect redacted operation progress with `uv run python -m scripts.account_deletion status` or `uv run python -m scripts.account_deletion status --operation <UUID>`. An operation that reports `failed` remains durable and is retried automatically; `uv run python -m scripts.account_deletion retry <UUID>` makes that failed operation due immediately. Run these commands only in the configured host environment for the target database. They do not accept an account ID or reveal a receipt, personal content or credentials. A `succeeded` receipt expires seven days after completion; losing the browser cookie cannot be repaired from host status.

Remote cleanup requires proven original destinations. Revision `r28_n8n_endpoint_lineage` records the credential-free n8n service root before dispatch; it deliberately leaves historical origins unknown. Existing remote resources with unknown origins, changed endpoint settings, unsettled sends, unavailable credentials or ambiguous peer ownership keep deletion failed/retryable. The operator must establish the original endpoint and reconcile its resources from trusted provisioning/provider records before retrying; never infer history from today's settings or clear a failed stage merely to obtain success. GitHub revocation requires an explicit supported success response; a lost/ambiguous provider response can require provider/operator investigation rather than automatic completion. These are application cleanup limits, separate from n8n execution history, provider logs and backups.

## Recovering erased bootstrap administration

Deleting account 1 deliberately leaves a sanitized disabled tombstone. Public first-run setup stays closed, including when `SETUP_TOKEN` is known. Recovering administration requires privileged shell/database access to the correct host. It creates a **new empty private workspace and password**; it restores no deleted content, credentials, integrations, memberships or old sessions. It does not issue a login session.

1. Isolate public ingress and stop the deployment's API, workers and automation publishers using its existing supervisor. Keep the target PostgreSQL service available. Do not remove containers' volumes, reset the database or restore a pre-deletion backup. Confirm the checkout/environment and effective target database privately; never paste connection credentials into logs or a support ticket.
2. Inspect `uv run python -m scripts.account_deletion status`. An incomplete/failed deletion must be repaired and allowed to finish first; use the existing retry command and worker recovery, then stop publishers again. Do not manually sanitize rows to make recovery pass. If the browser receipt was lost or its seven-day record expired, the recovery command still validates the durable tombstone and absence of identity references; host status cannot recreate the browser receipt.
3. From an interactive terminal in that deployment environment run `uv run python -m scripts.account_deletion recover-bootstrap --confirm-new-workspace`. Enter a new password of 12–128 characters twice at the hidden terminal prompts. Passwords cannot be supplied in command arguments or piped stdin. Do not run this command from a transcript-recording terminal.
4. The Auth-owned command locks account 1 using the existing lifecycle lock and refuses an active, absent or incompletely sanitized identity, any pending deletion operation, old sessions, owned workspaces, memberships or registered personal references. It provisions a new workspace and owner membership and activates the new hash in one transaction. Failure rolls back the new workspace and account changes. No receipt authorizes this host command, and it has no HTTP endpoint.
5. Restart the stopped services through the existing supervisor, sign in normally with the new password, and verify the workspace is empty. Review host environment secrets separately before enabling integrations. Restrict ingress again if validation fails.

This recovery procedure has focused unit checks; it has not been executed against a real deployment as part of implementation. Host backups and independent remote systems still need their own retention and restore handling.

## Cross-module read projections

Module persistence models stay private. The following SQL projections are approved for reads only; they grant no write access or separate agent/MCP authorization. Existing owner authentication and source/document visibility checks remain in force.

| Consumer | Owner fields read | Required fences |
| --- | --- | --- |
| Search retrieval (`modules/search/public.py`) | Source: `id,name,type,status,local_only`; document: `id,source_id,current_version,extraction_status,content_type,published_at,observed_at,title,canonical_url`; version: `id,document_id,version_number,observed_at`; chunk: `id,document_version_id,content` | Existing source/document/version/chunk joins; current revision; ready/succeeded extraction; active source. Recheck after provider calls. Lexical may include local-only sources; vector retrieval may not. |
| Search indexing (`modules/search/indexing.py`) | Source: `id,status,local_only`; document: `id,source_id,current_version,extraction_status`; version: `id,document_id,version_number`; chunk: `id,document_version_id,content` | Active, current, extracted and non-local-only eligibility. Hold the source row lock across provider transport and recheck before each send. Remote embeddings also require owner opt-in. |
| Current chunk backfill (`modules/knowledge/documents/public.py`) | Source: `id,status` | Active source, current document version and ready/succeeded extraction. Writes remain document-owned. |
| Raw storage cleanup and purge manifests | Document: `source_id,raw_uri` | Orphan detection includes every retained reference, including paused/archived sources and failed extraction. Purge manifests are scoped to the locked source and generation; keep path validation and retry handling. |
| Host-only bootstrap recovery (`core/auth/recovery.py`) | Registered table metadata: integer identity columns (`owner_id`, `account_id`, `user_id`, `*_user_id`) and direct foreign keys to `owner.id`; existence only, no payloads | Auth locks account 1, requires the exact sanitized disabled tombstone, loads the complete erasure owner registry, and refuses any remaining reference. This projection only checks absence; it never writes another module's tables. Workspace creation uses the public provisioning contract within the same transaction. |

Cross-module mutations use owner commands on the caller's `AsyncSession`; commands preserve source generation fences, row-lock ordering, and transaction boundaries without committing early.
