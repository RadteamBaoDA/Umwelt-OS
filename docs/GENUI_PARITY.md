# Generative UI parity matrix

Upstream: CopilotKit/OpenIntelligentUI @ `8391a94c1c3939c679e40ddd7bfc08a9ef690e70` (MIT).
Upstream paths come from the upstream git tree at that commit (apps/agent, apps/app, apps/mcp, packages/design-system).
Every upstream source file under `apps/` maps to at least one row. Umwelt-OS evidence and proof were re-verified against the
code on the integration branch; line numbers drift, so re-run `python scripts/check_genui_parity.py` after code moves.

Statuses: `ported`, `equivalent` (same user-visible behaviour through a different design), `excluded-by-owner`
(owner decision, reason in the evidence column), `not-ported` (real gap, must reach zero).

Rules enforced by `scripts/check_genui_parity.py`: every row has all columns, status is one of the four values,
every backticked path in the evidence and proof columns (a trailing `:line` is stripped) exists in the repo, and no
row is `not-ported`. A `not-ported` or `excluded-by-owner` row may use plain text (`none`, a reason) in
evidence/proof; other rows need non-empty text. Pending real-model, Docker and Playwright runs are written as
`pending:` plain text in the proof column and need owner approval.

Gate wiring: `make lint` and `./scripts/dev.ps1 lint` currently pass `--allow-not-ported` so the gap stays visible
without blocking. The final gate (end of the port) drops that flag so any remaining `not-ported` row fails lint.

## API and SSE contract: generative UI turns

- Persisted: assistant `Message.metadata_json` carries `generative_ui_parts: [{part_id, kind, status, ...slot}]` in render order; `generative_ui` is a copy of the first part (older clients). No schema migration (JSON). Cap: `GENERATIVE_UI_MAX_PARTS` (default 4, 1-8); extra presentation calls are ignored, an invalid call drops only its own part.
- `part_id`: the provider tool-call id (at most 64 chars); empty or repeated ids become `part-<n>`, and an id reused by a later round gets an `r<round>-` prefix so ids stay unique for the whole turn. It is identical in streaming snapshots and the final part.
- `GET /api/v1/conversations/{id}`: each message has `generative_ui` (first part or null) and `generative_ui_parts` (all valid parts; rows without the field fall back to the single `generative_ui`).
- SSE: `message.ui.delta` (one cumulative `status="streaming"` snapshot per part, with `part_id`; the client replaces by `part_id`), `message.ui.done` (one per completed part, with `part_id`), and `message.done` with `generative_ui` (first part) plus `generative_ui_parts`. Privacy cleanup drops both metadata keys and blanks every `message.ui.*` event of the run.
- History: later turns see a bounded summary of every completed part within one shared 4 KB budget.
- Rounds: presentation tools never end the turn. After a round's widgets the worker appends the assistant tool calls plus one `role: tool` result per call (`{"status":"rendered","part_id":...}`, no payload echo) and runs another model round, so the model can write text or add more widgets across rounds of one answer. The loop stops when a round has no actionable tool call, when total parts reach `GENERATIVE_UI_MAX_PARTS` (the cap counts parts across rounds), or after `GENERATIVE_UI_MAX_ROUNDS` widget rounds (default 3, 1-5; 1 restores the single-response behaviour). Text of all rounds is concatenated into one answer. `render_form` is a presentation tool like the others and may share a round with other parts.
- Data tools in the same loop: `read_skill`, `get_trip_stop_images`, `manage_todos` and `get_todos` share the `MAX_SKILL_ROUNDS` bound; `request_user_input` is bounded separately (2 per turn).
- Run statuses: `pending`, `streaming`, `awaiting_input` (active), then terminal `completed`, `cancelled`, `failed`. `awaiting_input` means the worker parked on a `request_user_input` call; it holds no lock or transaction while parked and counts as active (a second turn still gets 409).
- Human-in-the-loop SSE: `message.input.request` (`{request_id, kind: time_slots|choice|text, prompt, options, slots, expires_at}`) is appended when the run parks; `message.input.resolved` (`{request_id, outcome: answered|declined|expired, label?}`) when the owner answers via `POST /api/v1/responses/{id}/input`, or the request expires (the run is then cancelled with a `status` event). The answer resumes the same run (no new message). Privacy cleanup blanks both events and clears the stored request; an expired or cancelled request ends the run with no final message, citations or `message.done`.
- Ordering: widget `message.ui.delta` events published before parking stay valid; after resume, later rounds continue the same `seq` stream.
